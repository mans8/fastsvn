# FastSVN

> **开源免费的 macOS SVN 客户端（Subversion GUI）** —— 终于有一个不像 2005 年的 SVN 图形界面了。

还在用命令行敲 `svn commit`？还在为 Mac 上找不到好用的 SVN 客户端发愁（TortoiseSVN 只有 Windows，Cornerstone 又贵又久不更新）？**FastSVN** 是一个专为 macOS 打造的现代 Subversion 客户端：

- 🚀 **真实调用本机 `svn` 引擎** —— 不是 mock、不是假数据，你本地的 SVN 仓库直接接管
- 📦 **一键从服务器检出**，带真实进度条与下载速度
- 👀 **改动一目了然** —— 待提交 / 待更新分栏展示，差异高亮、支持大文件与目录级 diff
- 🌲 **完整浏览** —— 本地目录树 + 远程仓库浏览，提交、更新、冲突处理、历史日志全覆盖
- 🎨 **现代界面** —— 基于 BoardUI（React + Tailwind v4）语义 token 体系，亮/暗主题、组件、配色统一可调

> 📋 **[更新日志 / CHANGELOG](CHANGELOG.md)** —— 每个版本的详细修改记录。

## 从服务器检出

工具栏「从服务器检出」或空状态入口都能打开。填仓库地址 → 本地路径会自动推导（`~/Documents/<仓库名>`）→ 开始检出。

### 进度和速度是怎么来的

**svn 没有 `--progress`，非 TTY 下也不输出百分比。** 所以进度必须自己量，三步：

1. **预统计**：`svn list -R --xml <url>` 拿条目数与总字节（超过 20 秒放弃，退化为不确定进度条，检出照常进行）
2. **条目计数**：流式解析 checkout 的 stdout，数 `A    path` 行
3. **字节与速率**：每 600ms 遍历目标目录（**跳过 `.svn`**，否则元数据会让速率虚高），用 EMA 平滑得到瞬时速度

实测（6000 文件 / 18.1 MB 的本地仓库）：

| 时刻 | 进度 | 条目 | 已接收 | 速度 |
|---|---|---|---|---|
| 进行中 | 78% | 4719 / 6080 | 9.0 MB | 7.5 MB/s |
| 完成 | 100% | 6080 / 6080 | 18.1 MB | 平均 6.8 MB/s，用时 2.7 秒 |

**为什么是「条目」而不是「文件」**：`A` 行既包含文件也包含目录，所以分母必须算上目录才和进度条一致（6080 = 6000 文件 + 80 目录）。如果只写「文件 6080」会与成功提示里的「6000 个文件」矛盾，因此这里用「条目」。

### 三个安全约束

| 约束 | 原因 |
|---|---|
| 目标必须是空目录 | 否则 svn 会把新内容混进已有文件里 |
| 云同步目录会警告（iCloud / Dropbox / OneDrive / 坚果云 / 百度网盘） | 同步进程可能破坏 `.svn/wc.db`，这是**唯一能造成数据丢失**的场景 |
| 地址只接受 `http(s)://`、`svn://`、`svn+ssh://`、`file://` | 防止把本地路径当 URL 传给 svn |

检出成功后自动加入左侧项目列表，不用再手动添加一次。中途点「停止」会 `SIGTERM` 掉 svn 进程，目录保留，重新检出会接着下载。

## 打包成 macOS 应用

```bash
bash scripts/build-app.sh
open build/FastSVN.app
```

产物 `build/FastSVN.app`（约 112 MB，其中 108 MB 是内嵌的 node 运行时），可拖到 `/Applications` 双击启动。

架构很轻，没有用 Electron/Tauri：

- **启动器**（107 KB 的 Swift / AppKit 二进制）：拉起内嵌 `node` 子进程 → 从它的 stdout 读到 `LISTENING <port>` → 用 `WKWebView` 加载 `http://127.0.0.1:<port>` → 退出时 `SIGTERM` 收掉子进程（1.5 秒不退则 SIGKILL）
- **端口**：`PORT=0` 由系统分配，不会和正在运行的开发实例（5183）抢端口
- **数据目录**：`~/Library/Application Support/FastSVN/data`，更新应用不会覆盖用户的项目列表
- **日志**：`~/Library/Logs/FastSVN.log`，启动失败先看这里

验证记录（真机跑通）：

| 检查 | 结果 |
|------|------|
| `open build/FastSVN.app` 启动 | 窗口 `visible=true frame=1280x820` |
| 内嵌服务 | 系统分配端口 54861，`/api/status` 读到 7 个变更文件（39 ms） |
| 退出清理 | 日志出现「终止 node pid=85821」，进程列表已无残留 |
| 自测开关 | `FASTSVN_AUTOTERM=6 ./build/FastSVN.app/Contents/MacOS/FastSVN` 到点自动退出 |

尚未做代码签名与公证（ad-hoc 签名，本机运行没问题；发给别人需要 Developer ID 证书，否则会被 Gatekeeper 拦）。

## 运行

**后端（零依赖，只用 Node 内置模块）**

```bash
cd fastsvn
node server.js
# 打开 http://127.0.0.1:5183
```

服务端会自动优先提供 `web/dist`，找不到时回退到旧的 `public/`。所以后端不需要 `npm install`。

**前端**

```bash
cd fastsvn/web
npm install          # 首次
npm run build        # 产出 dist，刷新页面即生效
```

**前端热更新开发**：`cd web && npx vite` 起 5173，`/api` 自动代理到 5183。改组件保存后浏览器立即更新，不用反复 build。

想在真实数据上试，先建一个演示仓库：

```bash
bash scripts/demo-repo.sh          # 建 /tmp/fastsvn-demo-repo 与 /tmp/fastsvn-demo-wc
```

然后在应用里点「添加项目…」填 `/tmp/fastsvn-demo-wc`。

**要求**：机器上有 `svn`（`brew install subversion`）。应用会自动探测 `/opt/homebrew/bin/svn`、`/usr/local/bin/svn`、`/usr/bin/svn`。

## 架构

```
fastsvn/
├─ server.js          本地服务：svn 调用 + XML/diff 解析 + REST API
├─ public/
│  ├─ index.html      结构
│  ├─ style.css       四主题 token（CSS 变量 + data-theme）
│  └─ app.js          状态管理 + 渲染 + 交互
├─ scripts/
│  └─ demo-repo.sh    生成带各类变更状态的测试仓库
└─ data/
   └─ working-copies.json   工作副本列表（本地持久化）
```

### 引擎适配层（唯一出入口）

- **只调用官方 `svn` 实现**，绝不直接读写 `.svn` 目录。
- 只解析 `--xml` 与 unified diff，不解析人类可读的本地化文本。
- 所有命令用 `execFile` **参数数组**传参，不拼接 shell 字符串（防注入）。
- 强制 `--non-interactive`，避免卡在交互提示。

### API

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/health` | 引擎路径检测 |
| GET/POST/DELETE | `/api/working-copies` | 工作副本列表管理 |
| GET | `/api/status?path=&remote=1` | 状态 + 行数统计 + 风险标记 |
| GET | `/api/diff?path=&file=&kind=` | 解析后的 diff 行 |
| POST | `/api/commit` | 提交（`-m` + `--depth empty` + 指定文件） |
| POST | `/api/update` | 更新 + 冲突计数 |
| POST | `/api/revert` | 撤销（先快照再 revert） |
| GET | `/api/log?path=&limit=&verbose=1` | 版本日志，`verbose=1` 带每次提交的变更文件 |
| GET | `/api/conflict?path=&file=` | 读取文件里的冲突块（自动剥离 diff3 的 base 段） |
| POST | `/api/resolve` | 标记冲突已解决：`mine-full` / `theirs-full` / `working` |
| POST | `/api/add` | 加入版本管理（目录递归；`--force` 尊重用户主动意图） |
| POST | `/api/ignore` | 写入父目录 `svn:ignore`，已存在则幂等返回 |
| POST | `/api/delete` | 先快照再删除；未纳入的文件直接删本地 |
| POST | `/api/rename` | 已纳入的走 `svn move`（保留历史），未纳入的直接改名 |
| POST | `/api/cleanup` | 清理工作副本 |

**安全边界**：只监听 `127.0.0.1`；所有路径必须是绝对路径且含 `.svn`；文件路径必须落在工作副本内。

## 性能

本机实测（`file://` 仓库，2000 个文件、其中 60 个改动）：

| 环节 | 优化前 | 优化后 |
|------|--------|--------|
| 行数统计（diff） | 151 ms（**60 次子进程**） | 23 ms（**1 次子进程**） |
| 首次全量扫描（info + status + diff + 解析） | ≈ 171 ms | 118 ms |
| 重复请求（2s 内） | 重复全量 | **0 ms**（内存缓存命中） |
| 打开应用首屏 | 白屏等全量 | 读磁盘缓存即时渲染，后台再校验 |

**关键改动**：原来对每个变更文件起一次 `svn diff`，现在改成**一次 `svn diff` 覆盖整个工作副本**，再按 `Index:` 切分统计。进程调用从 `N+1` 降到 `2`，所以改动文件越多，差距越大（60 个文件时 6–8 倍）。

复现：

```bash
KEEP=1 node scripts/bench.js 2000    # 造仓库并打印对比数据，保留仓库供应用测试
```

三层缓存：

1. **进程合并**：N 次 diff → 1 次（结构性优化，收益最大）
2. **内存缓存**：2 秒内重复请求直接复用，写操作（提交/更新/撤销/解决冲突）后立即失效
3. **磁盘缓存**：状态落 `data/status-cache.json`，下次打开先渲染它（`?stale=1`），再后台全量校验

## 已知限制

1. **界面层不是原生 SwiftUI**。本机只有 Command Line Tools 没有 Xcode，SwiftUI 的 `@State` 等宏无法展开（`SwiftUIMacros` 插件缺失），所以界面用 WKWebView 承载，外壳是原生 AppKit。原生 SwiftUI 骨架保留在 `fastsvn-native-wip-*`，装 Xcode 后可继续。
2. **未做代码签名与公证**，只 ad-hoc 签名。本机双击可开，分发给他人的话需要 Developer ID 证书。
3. 冲突只处理**文本冲突**；树冲突/属性冲突目前只做识别。
4. 删除操作会先备份到快照目录，但**不做撤销按钮**，恢复需要去快照目录手工取回。
5. 访问受控目录（桌面/文稿）时，svn 子进程仍受 macOS TCC 约束。
6. 缓存以「工作副本」为粒度整体失效，不做单文件级增量比对（当前规模下够用）。
7. **检出进度依赖一次额外的 `svn list -R`**。超大仓库列目录可能超过 20 秒，此时进度条退化为不确定态（仍能检出，只是没有具体百分比）。
8. **检出速率是"已落盘字节/时间"**，不是协议层吞吐。走 `file://` 本地仓库时数值会很高（没有网络瓶颈），属正常。
9. **「待同步」有 30 秒缓存**。同事刚提交的改动，最多 30 秒后才出现在列表里；点「同步最新」或切页签时会立刻重查。
10. **仓库浏览的说明列有覆盖上限**：目录里文件版本跨度超过 600 时，只查最近 600 个版本的 log，更早的条目说明留空。这是为了避免在大仓库上一次拉几千条日志。
11. 仓库浏览的目录缓存只在窗口打开期间有效，关掉即失效；需要最新内容点「刷新」。
12. 文件预览只读前 512 KB，且不做语法高亮；二进制文件只报大小。仓库文件查看（`svn cat`）同样限 512 KB、最多渲染 3000 行。
12. 前端产物 662 KB（gzip 203 KB）。BoardUI + React Aria 占了大头，桌面应用内加载无感，但如果将来做 Web 版需要分包。
